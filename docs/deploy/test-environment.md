# Test environment (dev-only)

A private test deploy so teammates can use Brewed from anywhere. It has **no real users**: all data is fake and can be
wiped at any time. Testing rules, scenarios, and bug reporting are in [`../testing-plan.md`](../testing-plan.md).

| | |
|---|---|
| App + API | One Vercel project (Hobby plan), e.g. `https://brewed-xyz.vercel.app`. Vercel shows the exact URL |
| Database | Database `brewed-test` on MongoDB Atlas (Free), separate from everyone's local-dev data |
| Deploys | Every push to the production branch (config: [`vercel.json`](../../vercel.json)) |
| Accounts | The seeded accounts from `npm run seed`. The password is shared in the team chat, **never on GitHub** (the repo is public) |

---

## How it's put together

```text
browser ──▶ Vercel (one domain)
              /api/*, /uploads/*  ──▶ one function: api/index.js ──▶ Express app (backend/src/app.js)
              /assets/*, files    ──▶ CDN: the built React app (frontend/dist)          │
              anything else       ──▶ index.html, so deep links like /cafes/123 work     ▼
                                                              Atlas: brewed-test (data + images)
```

The frontend and the API share **one domain**, which removes most deploy problems:

| Problem | How this setup handles it |
|---|---|
| The auth cookie is `sameSite: "lax"`, so an API on another site never receives it and login silently fails | Same domain, so the cookie is always sent. `api/index.js` runs in production mode, so the cookie is also `secure` |
| CORS allows exactly one origin (`CLIENT_URL`) | Same-origin requests don't use CORS, so `CLIENT_URL` doesn't need to be set |
| `VITE_API_URL` is baked in at build time | Production builds call their own domain by default (`frontend/src/lib/api.js`), so there's nothing to set |
| A refresh on a deep link 404s on static hosts | `vercel.json` sends every unknown path to `index.html` |
| A Vercel function has no lasting disk, so disk uploads would vanish | Images are stored in MongoDB (`backend/src/models/Upload.js`) |
| Vercel refuses any request over **4.5 MB**, and phone photos are often bigger | The browser shrinks photos over 1 MB to 1600 px JPEGs first (`frontend/src/lib/shrinkImage.js`), about 0.3 MB for a 12-megapixel photo |
| A function has no startup step to connect to MongoDB | `api/index.js` connects on the first request and reuses the connection |

CI ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)) builds the frontend and runs the 106 API smoke checks against
`api/index.js` on every PR.

## One-time setup

Ren does steps 1–5. Wion (org owner) may need to approve one GitHub request in step 2.

1. **Atlas: database, user, network access**
   - No cluster yet? *Create → Free*, provider **AWS**, region **Singapore (ap-southeast-1)**. That's next to Vercel's `sin1`
     region set in `vercel.json`. If the team's cluster is in another region, change `"regions"` in `vercel.json` to the
     [nearest Vercel region](https://vercel.com/docs/regions). Otherwise every query crosses an ocean.
   - *Database Access → Add New Database User*: user `brewed-test`, an autogenerated password,
     *Specific Privileges* → `readWrite` on database `brewed-test`. It can't touch anyone else's data.
   - *Network Access → Add IP Address → Allow access from anywhere* (`0.0.0.0/0`). Vercel functions don't have fixed IPs
     on the free plan, so there's nothing narrower to allow. The scoped user and its password are what protect the data.
   - *Connect → Drivers*: copy the `mongodb+srv://…` string and insert the database name:
     `mongodb+srv://brewed-test:<password>@<cluster-host>/brewed-test?retryWrites=true&w=majority`
2. **Vercel: import the repo.** Sign up at vercel.com *with GitHub* (Hobby plan). *Add New → Project*.
   If `Webiverse-Labs/brewed` isn't listed, click *Adjust GitHub App Permissions*, pick `Webiverse-Labs`, and give access to
   `brewed` only. GitHub then asks an org owner (Wion) to approve. Hobby can deploy public repos owned by an org.
3. **Vercel: configure before the first deploy**
   - Framework Preset: *Other*. Root Directory: the repo root (`./`). Leave the build settings alone, since `vercel.json` sets them.
   - Environment Variables:

     | Name | Value |
     |---|---|
     | `MONGO_URI` | The connection string from step 1 |
     | `JWT_SECRET` | Output of `openssl rand -hex 32` (any long random string) |

   - Click *Deploy*.
4. **Production branch.** Vercel treats `main` as production, but the backend isn't merged yet. Until PR #1, `backend/api` and
   `deploy/test-env` are merged, set *Settings → Environments → Production → Branch Tracking* to `deploy/test-env`, then redeploy.
   Switch it back to `main` after the merges.
5. **Seed the test database** from your machine. Create `backend/.env.test` (git-ignored) with:

   ```env
   MONGO_URI=<the connection string from step 1>
   SEED_PASSWORD=<a new password, 16+ random characters>
   ```

   ```bash
   cd backend
   node --env-file=.env.test src/seed.js
   ```

   Every seeded account uses `SEED_PASSWORD`, including `admin@brewed.app`. Those emails are public in `seed.js`, so this
   password is the only thing protecting them. Don't reuse your local one.
6. **Check it** with the post-deploy check below, then post the URL and the password in the team chat.

**If the GitHub approval takes too long**, deploy from your machine instead. Env vars are set in the dashboard the same way,
but pushes don't auto-deploy:

```bash
npx vercel login
npx vercel link
npx vercel --prod
```

## Post-deploy check (5 minutes)

Do this after the first deploy and after any deploy that changes auth, uploads, or `vercel.json`.

- [ ] `<url>/api/health` shows `{"ok":true}`
- [ ] Log in as `margotbrews@example.com`. Home shows the cafés
- [ ] Open a café, then **refresh**. The page reloads and you stay logged in
- [ ] Settings → upload a **real phone photo** as the avatar. It shows up, and it's still there after a refresh
- [ ] `<url>/admin/login` as `admin@brewed.app`: the dashboard numbers load
- [ ] Log out. Visiting `/profile` sends you to `/login`

## Day to day

| Task | How |
|---|---|
| Deploy | Push to the production branch. Vercel builds in about a minute (dashboard → *Deployments*) |
| Preview a branch | Every other branch gets its own preview URL. On Hobby, only you can open previews (Vercel login). Teammates use the production URL |
| Reset the data | `node --env-file=.env.test src/seed.js --reset` in `backend/`. This deletes **all** users, logs, and images. Say so in the team chat first |
| Read server logs | Vercel → project → *Logs* |
| Undo a bad deploy | *Deployments* → an earlier production deployment → *Instant Rollback*, or revert the commit |
| Change a secret | *Settings → Environment Variables*, then redeploy. Running deployments keep the old value |

Don't run `npm run smoke` against the test env. It signs up, suspends, and deletes accounts. CI runs it on a throwaway database.

## Known limits (accepted for a dev-only env)

- **Atlas is open to any IP** (`0.0.0.0/0`, see step 1). Keep the `brewed-test` user scoped to its one database.
- **No login rate limiting.** Anyone who finds the URL can try passwords, so the seed password must be strong.
- **4.5 MB per request.** Photos are shrunk first, but a big GIF isn't (shrinking would drop the animation). Too-large uploads show "Those photos are too big to send together".
- **Images count against Atlas Free's 0.5 GB.** Atlas Free also has no backups, allows 100 operations per second, and pauses after 30 days without connections.
- **Vercel Hobby is for non-commercial use only.** A school project qualifies.
- "Forgot your password?" only shows a "coming soon" toast. If a tester forgets the password, share it again.

## Before real users (not needed now)

Move images to object storage (Vercel Blob, Cloudinary, or S3) with direct browser uploads. Add rate limiting on `/api/auth/*`.
Set up a separate production database with backups, a custom domain, and error monitoring.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Every API call returns 503 "The database is unavailable" (after ~10 s) | Atlas *Network Access* doesn't allow `0.0.0.0/0`, or `MONGO_URI` is wrong or has the wrong password. Check Vercel *Logs* |
| Build fails with `vite: not found` | The install step skipped the frontend's dev dependencies. Compare the Install Command with `vercel.json` |
| `/api/...` returns the React app or a Vercel 404 | Root Directory isn't the repo root, so `vercel.json` and `api/` weren't picked up |
| Login succeeds, then you're sent back to `/login` | The browser is blocking the cookie: use the production URL, and check for extensions or strict privacy settings |
| "Those photos are too big to send together" | Over 4.5 MB in one request. Upload fewer photos at a time |
| Every page is slow (1 s+ per click) | The function region (`vercel.json`) and the Atlas region are far apart |
